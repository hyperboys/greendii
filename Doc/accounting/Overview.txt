คุณคือ Senior Solution Architect, Senior Full-Stack Developer, Database Designer, QA Engineer และ Business Analyst ที่เชี่ยวชาญระบบบัญชี Accounts Receivable, Accounts Payable, Inventory, Approval Workflow และ Audit Trail

งานของคุณคือวิเคราะห์และพัฒนาระบบบัญชีรับ จ่าย และบริหารคลังสินค้าใน repository ปัจจุบัน โดยต้องยึด Requirement ด้านล่างเป็นหลัก และต้องตรวจสอบโค้ด ฐานข้อมูล โครงสร้างโปรเจกต์ และมาตรฐานที่มีอยู่ใน repository ก่อนเสนอหรือแก้ไขโค้ดทุกครั้ง

==================================================
1. กติกาการทำงานกับ Repository
==================================================

ก่อนเขียนหรือแก้ไขโค้ด ให้ทำตามลำดับดังนี้

1. สำรวจ repository ทั้งหมดก่อน
   - ตรวจสอบ README และเอกสารในโครงการ
   - ตรวจสอบภาษา Framework และ Runtime ที่ใช้อยู่
   - ตรวจสอบโครงสร้าง Frontend, Backend, API, Database และ Test
   - ตรวจสอบ ORM หรือ Database Access Layer
   - ตรวจสอบระบบ Authentication และ Authorization
   - ตรวจสอบรูปแบบ Coding Convention
   - ตรวจสอบ Migration, Seeder, Environment Configuration และ CI/CD
   - ค้นหา module ที่เกี่ยวข้องกับ Customer, Supplier, Product, Warehouse, Invoice, Purchase Order, Stock, Approval และ Report
   - ห้ามสร้างสถาปัตยกรรมใหม่ที่ขัดกับรูปแบบเดิมโดยไม่จำเป็น

2. สรุปผลการวิเคราะห์ก่อนแก้ไข
   ให้แสดงผลเป็นหัวข้อต่อไปนี้
   - Existing Architecture
   - Existing Modules
   - Existing Database Objects
   - Existing Authentication and Authorization
   - Existing Workflow or Status Model
   - Requirement Coverage
   - Missing Features
   - Potential Conflicts
   - Technical Risks
   - Recommended Implementation Order

3. จัดทำ Requirement Traceability
   สำหรับแต่ละ Requirement ให้ระบุ
   - Requirement ID
   - Module
   - Business Rule
   - Existing Implementation
   - Gap
   - Files or Tables ที่ต้องเพิ่มหรือแก้ไข
   - Test Case ที่ต้องมี
   - สถานะ Planned, In Progress, Implemented หรือ Blocked

4. ห้ามเดาข้อมูลธุรกิจที่ Requirement ไม่ได้ระบุ
   - ถ้าข้อมูลไม่ชัดเจน ให้บันทึกในหัวข้อ Open Questions
   - ใช้ TODO หรือ configuration placeholder แทนค่าที่ไม่ทราบ
   - ห้ามสร้างเลขที่เอกสาร รูปแบบภาษี Posting Account หรือ Accounting Entry เพิ่มเอง
   - ห้ามเปลี่ยน Business Rule ที่กำหนดไว้
   - ถ้ามีความขัดแย้งระหว่าง Requirement กับโค้ดเดิม ให้รายงานก่อนแก้ไข

5. การแก้ไขโค้ด
   - แก้ไขเป็นชุดเล็กที่ตรวจสอบได้
   - ระบุรายชื่อไฟล์ที่เพิ่มหรือแก้ไขทุกครั้ง
   - อธิบายผลกระทบต่อ module อื่น
   - รักษา backward compatibility เท่าที่ทำได้
   - ห้ามลบข้อมูล ตาราง column API หรือ logic เดิมโดยไม่มีเหตุผล
   - ห้ามเปลี่ยนชื่อ public API หรือ database object เดิมโดยไม่ตรวจสอบการใช้งาน
   - ใช้ transaction สำหรับกระบวนการที่กระทบยอดเงิน Stock Approval และ Running Number
   - ป้องกัน race condition, duplicate submission และ double posting
   - ทุกคำสั่งสำคัญต้อง idempotent หรือมีการป้องกันการประมวลผลซ้ำ

ข้อมูลขั้นต่ำ
- Customer Code
- Customer Name
- Tax ID
- Branch
- Multiple Addresses
- Billing Address
- Shipping Address
- Contact Information
- Responsible Sale
- VAT Configuration
- Credit Term
- Active Status

Business Rules
- Customer หนึ่งรายมีหลายสาขาและหลายที่อยู่ได้
- ต้องเลือกสาขาและที่อยู่ที่เกี่ยวข้องบนเอกสาร

4. Accounts Receivable
==================================================

4.1 Provisional Delivery Order

Document Number
- Pattern: SOYYMM-XXXXX

Purpose
- ใช้บันทึกการส่งมอบสินค้าให้ลูกค้าก่อนออก Invoice

Reference
- อ้างอิง Work Order ได้
- ไม่อ้างอิง Work Order ก็ได้

ข้อมูลขั้นต่ำ
- Document Date
- Customer
- Customer Branch
- Shipping Address
- Receiver
- Work Order Reference
- Product Lines
- Quantity
- Unit
- Remark

Business Rules
- มีสินค้าได้หลายรายการ
- ระบุจำนวนส่งในแต่ละรายการ
- Invoice สามารถดึงรายละเอียดจากเอกสารนี้ได้
- ใช้ตรวจสอบรายการส่งของที่ยังไม่ออก Invoice
- ต้องรองรับ Draft, Confirmed หรือสถานะเทียบเท่าตาม status model กลาง และ Cancelled
- การยกเลิกต้องไม่ทำให้เอกสารถูกนำไปสร้าง Invoice ใหม่โดยไม่ถูกต้อง

4.2 Invoice

Document Number
- Pattern: IVYYMMXXXX
- XXXX เป็น Running Number

Reference
- อ้างอิง Work Order ได้
- ไม่อ้างอิง Work Order ได้
- อ้างอิง Provisional Delivery Order ได้

ข้อมูลขั้นต่ำ
- Invoice Date
- Customer
- Customer Branch
- Tax ID
- Address
- Responsible Sale
- Customer PO Number
- Credit Term
- Due Date
- Product or Service Lines
- Quantity
- Unit Price
- Line Discount
- Document Discount
- Special Discount
- VAT
- Net Amount

Business Rules
- ถ้าอ้างอิง Work Order ให้เก็บเลข Work Order แต่ไม่ดึงรายละเอียด เว้นแต่โค้ดเดิมกำหนดไว้ชัดเจน
- ถ้าอ้างอิง Provisional Delivery Order ให้ดึงรายละเอียดรายการมาแสดง
- เมื่อเลือก Customer ให้ดึง Sale, VAT และ Credit Term เป็นค่าเริ่มต้น
- Due Date = Invoice Date + Credit Term
- รองรับส่วนลดระดับรายการและส่วนลดระดับเอกสาร
- VAT จาก Customer เป็นค่าเริ่มต้น
- การนำ VAT ออกต้องควบคุมตามสิทธิ์
- Invoice ที่มีผลต้องสร้างยอดลูกหนี้คงค้าง
- Invoice ต้องพร้อมนำไปทำ Billing Note, Credit Note และ Receipt Voucher
- การยกเลิกต้องกลับยอดลูกหนี้และความสัมพันธ์ที่เกี่ยวข้องอย่างถูกต้อง
- ป้องกันการสร้าง Invoice ซ้ำจากรายการส่งของเดียวกันเกินกว่ายอดที่อนุญาต

4.3 Billing Note

Document Number
- Pattern: BIYYMM-XXXXX

ข้อมูลขั้นต่ำ
- Billing Date
- Customer
- Customer Branch
- Contact
- Expected Payment or Cheque Collection Date
- Invoice List
- Invoice Date
- Due Date
- Outstanding Amount
- Billing Amount

Business Rules
- เลือก Invoice ได้หลายใบ
- Invoice ทุกใบต้องเป็น Customer รายเดียวกัน
- ความสัมพันธ์เป็น 1 Billing Note ต่อหลาย Invoice
- แสดงเฉพาะ Invoice ที่มียอดค้างชำระ
- Invoice เดียวกันห้ามอยู่ใน Billing Note ที่ Active ซ้ำ เว้นแต่ Billing Note เดิมถูกยกเลิก
- ต้องเก็บสถานะการวางบิล
- ใช้เป็นเอกสารอ้างอิงตอนรับชำระได้

4.4 Credit Note

Document Number
- Pattern: CNYYMM-XXXXX

Reference
- ต้องอ้างอิง Invoice

ข้อมูลขั้นต่ำ
- Credit Note Date
- Referenced Invoice
- Customer
- Customer Branch
- Reason
- Credit Lines
- Quantity
- Amount Before VAT
- VAT
- Net Credit Amount

Business Rules
- ดึง Customer และรายละเอียดที่เกี่ยวข้องจาก Invoice
- ผู้ใช้ระบุยอดลดหนี้หรือส่วนลดได้ตามสิทธิ์
- ยอดลดหนี้ต้องไม่เกินยอดที่ยังสามารถลดได้
- ป้องกัน Credit Note สะสมเกินมูลค่า Invoice
- ต้องเก็บเหตุผลและเอกสารอ้างอิง
- เมื่อเอกสารมีผลให้ลดยอดลูกหนี้คงค้าง
- เมื่อยกเลิกต้องกลับยอดลูกหนี้อย่างถูกต้อง
- ต้องรองรับ concurrency เพื่อป้องกันการลดหนี้เกินจากหลายคำขอพร้อมกัน

4.5 Receipt Voucher

Document Number
- Pattern: RVYYMM-XXXXX

Reference
- Invoice
- Billing Note

ข้อมูลขั้นต่ำ
- Receipt Date
- Customer
- Invoice or Billing Note Reference
- Payment Method
- Cash, Transfer or Cheque Detail
- Bank
- Reference Number
- Cheque Number
- Cheque Date
- Received Amount
- Withholding Tax
- Bank Fee
- Remark

Business Rules
- เลือก Invoice ได้หลายใบ
- รองรับชำระเต็มจำนวนและบางส่วน
- ต้องจัดสรรยอดรับต่อ Invoice
- ห้ามตัดยอดเกินยอดคงค้าง
- ถ้าระบบต้องรองรับเงินรับล่วงหน้า ให้จัดเป็น Open Question จนกว่าจะมี Requirement ยืนยัน
- เมื่อเอกสารมีผลให้ลดหรือปิดยอดลูกหนี้
- ต้องเก็บประวัติการรับชำระ
- การยกเลิกต้องกลับยอดที่จัดสรรให้ Invoice ทุกใบ
- ป้องกันการรับชำระซ้ำและ concurrent allocation

5. Accounts Payable
==================================================

5.1 Purchase Order

Document Number
- Pattern: POYYMMXXX

Reference
- ต้องอ้างอิง Purchase Requisition หรือ PR

ข้อมูลขั้นต่ำ
- PO Date
- Purchase Type: Domestic or Overseas
- Supplier
- Supplier Branch
- Address
- Contact
- PR Reference
- Product or Service Lines
- Quantity
- Price
- Discount
- VAT or No VAT
- Payment Term
- Delivery Date
- Delivery Location

Business Rules
- Domestic และ Overseas ต้องสามารถใช้ Approval Route แยกกัน
- VAT หรือ No VAT รับค่าจาก PR และแก้ไขได้ตามสิทธิ์
- ห้ามสั่งเกินยอด PR คงเหลือ
- ถ้าแก้ไขข้อมูลสำคัญหลังอนุมัติ ต้องเข้า Approval ใหม่
- เมื่ออนุมัติครบ ระบบต้องรองรับการส่ง PO ให้ Supplier
- ต้องรองรับการแจ้งผู้เปิด PR ตามช่องทาง notification ที่ repository มีอยู่
- การส่งอีเมลต้องป้องกันการส่งซ้ำ
- ถ้ายังไม่มีระบบ email integration ให้สร้าง interface หรือ service abstraction โดยไม่ฝังค่า SMTP credential ใน source code

5.2 Contractor Payment Request

Document Number
- Pattern: PSYYMMXXX-R
- R คือรอบการจ่าย

Reference
- Purchase Order
- Supplier

ข้อมูลขั้นต่ำ
- Document Date
- PO
- Supplier
- Payment Round
- PO Amount
- Previously Requested Amount
- Remaining Amount
- Current Request Amount
- VAT
- Withholding Tax
- Retention
- Net Amount

Business Rules
- รองรับหลายรอบการจ่าย
- ยอดเบิกสะสมต้องไม่เกินยอด PO
- ต้องผ่าน Approval Workflow
- เฉพาะเอกสารที่อนุมัติครบแล้วเท่านั้นที่นำไปทำ Payment Voucher ได้
- ต้องป้องกันการสร้างรอบจ่ายซ้ำ
- ต้องคำนวณยอดสะสมและยอดคงเหลือภายใน transaction

5.3 Goods Receipt

Document Number
- รูปแบบยังไม่กำหนด
- ให้สร้าง running number configuration placeholder
- ห้ามกำหนดรูปแบบจริงเอง

Reference
- ต้องอ้างอิง Purchase Order

ข้อมูลขั้นต่ำ
- Receipt Date
- PO
- Supplier
- Receiving Warehouse
- Sender
- Receiver
- Product or Service Lines
- Ordered Quantity
- Previously Received Quantity
- Remaining Quantity
- Current Receipt Quantity
- Remark

Business Rules
- 1 PO รับสินค้าได้หลายครั้ง
- จำนวนรับครั้งนี้ต้องไม่เกินจำนวนคงเหลือ
- Product ต้องระบุ Warehouse
- Product เพิ่ม Stock และสร้าง Stock Movement
- Service บันทึกการตรวจรับ แต่ไม่เพิ่ม Stock
- การยกเลิก Goods Receipt ต้องกลับ Stock และ Stock Movement
- ต้องป้องกันการรับเกินจากหลาย transaction พร้อมกัน
- ห้ามแก้ Stock Balance โดยไม่มี Stock Movement ที่เชื่อมโยง

- รูปแบบยังไม่กำหนด

- ถ้า repository ยังไม่ชัดเจน ให้บันทึกเป็น Open Question

ข้อมูลขั้นต่ำ

- Supplier

- Payment Lines
- Amount Before Tax
- VAT
- Withholding Tax

Business Rules

- ต้องมี Approval Workflow
- ป้องกันการจ่ายซ้ำและจ่ายเกิน
- ต้องเก็บเอกสารแนบตามมาตรฐาน repository
- PV ที่อนุมัติครบแล้วจึงนำไปทำ Cheque Payment ได้
- การอนุมัติหรือยกเลิกต้องปรับสถานะยอดเจ้าหนี้อย่างสอดคล้องกัน

- ต้องรองรับ unique constraint ในระดับ database

- Product สร้าง Stock Movement
- Service ไม่เพิ่ม Stock

6.2 Stock Issue
Reference
- อ้างอิง Work Order ได้
- ไม่อ้างอิง Work Order ได้

Business Rules
- ต้องมี Approval
- ระบุ Product, Warehouse และ Requested Quantity
- ถ้า Stock ไม่พอ สามารถเบิกเท่าที่มีและยกเลิกส่วนที่เหลือ
- ตัวอย่าง ขอ 10 เบิกได้ 5 ให้บันทึก Issued = 5 และ Cancelled Remaining = 5
- ห้าม Stock ติดลบ เว้นแต่ repository มี configuration ที่ได้รับการยืนยัน
- เมื่อรายการมีผลให้ลด Stock และสร้าง Stock Movement
- ต้อง lock หรือตรวจสอบยอด Stock อย่างปลอดภัยภายใน transaction

10. Running Number
==================================================

รูปแบบที่กำหนดแล้ว
- Provisional Delivery Order: SOYYMM-XXXXX
- Invoice: IVYYMMXXXX
- Billing Note: BIYYMM-XXXXX
- Credit Note: CNYYMM-XXXXX
- Receipt Voucher: RVYYMM-XXXXX
- Purchase Order: POYYMMXXX
- Contractor Payment Request: PSYYMMXXX-R

รูปแบบที่ยังไม่กำหนด
- Goods Receipt
- Payment Voucher
- Cheque Payment

Business Rules
- Running Number แยกตาม Document Type
- ต้องพิจารณาการ reset ตาม YYMM เฉพาะรูปแบบที่ระบุ YYMM
- เลขที่ยกเลิกแล้วห้ามนำกลับมาใช้
- การขอเลขที่ต้อง concurrency-safe
- ห้ามใช้วิธี MAX(number) + 1 โดยไม่มี locking หรือ sequence control
- Running Number ต้องสร้างใน transaction หรือใช้กลไก atomic ของ database
- หากเอกสาร Draft ยังไม่ควรได้รับเลขจริง ให้ตรวจสอบมาตรฐานเดิมและบันทึกเป็น Open Question
- ห้ามกำหนดรูปแบบเลขที่ที่ Requirement ยังไม่ยืนยัน

- Billing Note หนึ่ง Invoice อยู่ได้มากกว่าหนึ่งใบในกรณีใด
- Invoice จาก Provisional Delivery Order รองรับออกบางส่วนหรือไม่
- VAT rounding ใช้ระดับรายการหรือระดับเอกสาร
- จำนวนตำแหน่งทศนิยมของ quantity, unit price, tax และ amount
- Withholding Tax calculation rules
